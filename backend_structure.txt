4.7 Logout
Logout should revoke the current refresh session using revoked_at and clear browser authentication cookies. The short-lived access token naturally expires.
5. Role Architecture
A Role represents the employee's broad organizational identity. The current roles are:
1  admin
2  Guest
3  HR
4  accountant
5  developer
6  business
The current architecture uses ONE primary role per employee:
employees.role_id → roles.id
Role is not the same as operational context.
6. Context Architecture
A Context represents the operational capacity in which an employee works.
1  Global
2  Agent
3  Relationship Manager
An employee can have multiple contexts. For example, Business Test 1 can have both AGENT and RM contexts while retaining one primary role.
6.1 Employee Context
Employee
   ↓
employee_contexts
   ↓
Context
employee_contexts stores employee_id, context_id, reports_to_id, is_default, is_active, and audit/deletion information.
6.2 Active/Default Context
One context can be the employee's default context. The active context determines which context-specific permissions are currently used.
7. Permission Architecture
A Permission represents a specific action.
employees:view
employees:create
employees:update
applications:view
applications:create
applications:update
Permissions are stored in permissions. The permission code is the application-level identifier.
7.1 Permission Assignment
Permissions are assigned to an employee's context, not simply to the employee.

9. Hierarchy & Data Scope
Permissions answer 'Can the employee perform this action?' Data scope answers 'Which records can the employee access?'
Permission
    +
Hierarchy / Ownership / Data Scope
    =
Actual Data Access
employee_contexts.reports_to_id stores the reporting relationship and can be used by backend services to determine an employee's operational scope.

9.2 Agent Access
An Agent with applications:view should not automatically see every application. The backend combines the permission with the Agent's permitted/assigned data scope.
9.3 RM Access
An RM may access their own applications and applications belonging to agents in their permitted hierarchy, according to the backend service rules.

11. Backend Authorization
The backend is the final security boundary. Frontend permission checks are for UI/UX and cannot be trusted as the final authorization mechanism.

This architecture keeps identity, organizational role, operational context, actions, and record-level scope separate. That separation is the foundation of the Runamarga CRM authorization model.
Concept | Question | Responsibility
Authentication | Who is this employee? | Proves identity and creates an authenticated session.
Role | What is the employee's broad organizational role? | Identifies the primary organizational role.
Context | In which operational capacity is the employee working? | Defines the employee's operating context.
Permission | What actions are allowed? | Defines specific actions such as view/create/update.
Data Scope | Which records can the employee access? | Limits records according to ownership/hierarchy.

Property | Access JWT | Refresh JWT
Purpose | Access protected APIs | Renew the authenticated session
Intended lifetime | 30 minutes | 7 days
Database | Not stored | Hash stored in auth_tokens
Employee ID | sub | sub
Revocation | Short-lived | Can be revoked via auth_tokens

Question | Answer
1. WHO? | Employee / Authentication
2. WHAT ROLE? | Primary Role
3. WHERE / IN WHICH CAPACITY? | Active Context
4. WHAT CAN THEY DO? | Permissions
5. WHICH RECORDS? | Data Scope / Hierarchy

Rule | Meaning
Role ≠ Context | Role is the broad organizational role; Context is the operational capacity.
Context ≠ Permission | AGENT/RM/GLOBAL does not itself grant an action.
Permission ≠ Data Scope | applications:view does not automatically grant access to every application.
One employee can have multiple contexts | The employee still has one primary role.
Permissions belong to employee-context | Permission assignment is context-specific.
Frontend is not the final security boundary | Backend permission and data-scope checks must enforce actual access.
Use permission codes | Seeders/checks should use permission codes rather than hard-coded IDs.

Table | Purpose
roles | Primary organizational roles.
employees | Employee identity, status, and primary role.
contexts | Operational contexts.
employee_contexts | Assigns contexts and stores hierarchy/default information.
permissions | Defines available actions.
employee_context_permissions | Assigns permissions to a specific employee context.
employee_details | Personal, employment, financial, and identity details.
auth_tokens | Hashed refresh-session information.
