RUNAMARGA CRM BACKEND
Architecture and Source Inventory
Last reviewed: 2026-10-19

==========================================================================
1. PURPOSE AND SCOPE
==========================================================================

This document is the technical map for the FastAPI backend in backend/. It
records the runtime design, module ownership, and current source inventory so
that a developer can locate the correct layer before making a change.

Included in the maintained-source inventory:
- Application Python modules, configuration, SQL trigger definitions, and
  Alembic migration source.
- Backend root configuration and dependency files.

Documented but intentionally not enumerated file-by-file:
- backend/.venv/: local virtual environment; not application source.
- **/__pycache__/** and *.pyc: generated Python bytecode.
- backend/app/static/uploads/** (13 files) and
  backend/app/services/static/uploads/** (3 files): runtime/user-uploaded
  data. These are not source-code assets.
- backend/runamarga_new_before_shuffle_migration.dump: database export;
  restricted operational artifact.

Current source counts:
- 306 Python modules under backend/app/ (excluding the virtual environment
  and generated bytecode).
- 66 route modules, 57 controller modules, 59 service modules, 51 models,
  and 39 schemas.
- 68 Alembic revision files.


==========================================================================
2. SYSTEM OVERVIEW
==========================================================================

Runtime stack
- API framework: FastAPI.
- ORM and migrations: SQLAlchemy 2.x and Alembic.
- Database driver: PostgreSQL through psycopg.
- Validation: Pydantic 2.x.
- Authentication: JWT and cookie-oriented security helpers.
- Real-time features: FastAPI WebSocket routes and in-process listeners.
- Files: FastAPI StaticFiles serves app/static/uploads at /uploads.
- Face workflows: InsightFace, ONNX Runtime, OpenCV, Pillow, NumPy, and
  supporting imaging libraries.

Application entry points
- HTTP admin API: /api/... via app.routes.admin.
- Android/API surface: /android/... via app.routes.api.
- WebSocket endpoints: registered without an additional prefix.
- Static uploads: /uploads/...

High-level request path

Client -> FastAPI route -> controller -> service -> SQLAlchemy -> PostgreSQL
                                                    |
                                             Pydantic/JSON response

Cross-cutting concerns
- Authentication and token validation: core/security.py and core/api_security.py.
- Authorization/data scope: core/access_control.py and dependency helpers.
- Logging/auditing: audit/, log_config.py, audit-log models/services/routes.
- Validation: schemas/ at API boundaries.
- File persistence: utils/file_upload.py and static upload storage.


==========================================================================
3. STARTUP, LIFECYCLE, AND ROUTING
==========================================================================

backend/app/main.py
- Creates the FastAPI application with an async lifespan.
- Applies database triggers before listeners are started.
- Discovers async listener functions named listen_* in app/listeners/.
- Cancels and awaits listener tasks during shutdown.
- Mounts /uploads from app/static/uploads.
- Registers CORS for the configured local frontend origin.
- Mounts the admin router at /api, API/mobile router at /android, and
  WebSocket router without a prefix.

Router composition
- app/routes/admin/__init__.py is the admin-router composition root.
- app/routes/api/__init__.py is the Android/API composition root.
- app/routes/admin/websockets/__init__.py is the WebSocket composition root.
- Individual route files declare endpoint contracts and delegate work to the
  controller/service layers.

Startup and background components
- database_triggers/runner.py installs or updates the reminder SQL trigger.
- listeners/reminder_listener.py contains the automatically discovered
  reminder listener.
- scheduler/ contains reminder scheduling utilities. Its deployment command
  and process ownership must be explicit when scheduling is enabled.


==========================================================================
4. LAYER RESPONSIBILITIES
==========================================================================

Layer                 Responsibility
--------------------  ------------------------------------------------------
routes/               HTTP/WebSocket endpoint declaration, dependency
                      wiring, and response/status handling.
controllers/          Request orchestration and hand-off to business logic.
services/             Business rules, transactions, query composition, and
                      domain-level authorization decisions.
schemas/              Pydantic input/output contracts and serialization.
models/               SQLAlchemy table mappings, relations, and persistence
                      metadata.
core/                 Security, access control, logging, and WebSocket auth.
dependency/           Reusable FastAPI dependency injection adapters.
config/               Environment-backed settings and database session setup.
audit/                Reusable audit logging contract and implementation.
seeders/              Controlled bootstrap/reference-data population.
migrations/           Versioned database schema evolution through Alembic.
utils/                Shared technical helpers such as upload persistence.

Boundary rules
- Routes do not contain business queries that belong in services.
- Controllers do not duplicate validation already represented by schemas.
- Services receive request-scoped SQLAlchemy sessions and do not keep ORM
  entities in a process-wide cache.
- Database schema changes require a new Alembic revision; do not edit an
  applied historical migration.
- Endpoint authorization is enforced server-side. Frontend visibility is not
  an authorization boundary.

Migration operating rules
- Generate a new revision for every schema, index, constraint, or data
  backfill change.
- Verify a single intended Alembic head before release; merge revisions only
  when parallel branches legitimately create multiple heads.
- Run upgrades against a disposable database before production.
- Back up and test reversibility for destructive data/schema operations.

14. CONFIGURATION, SECURITY, AND OPERATIONS
==========================================================================

Environment values currently read by app/config/settings.py
- DATABASE_HOST
- DATABASE_PORT
- DATABASE_NAME
- DATABASE_USER
- DATABASE_PASSWORD
- RESEND_API_KEY
- MAIL_FROM_ADDRESS (default: noreply@runamarga.com)
- MAIL_FROM_NAME (default: Runamarga Team)

Operational safeguards
- Keep .env outside version control; .env.example contains names only.
- Keep database exports and uploaded identity/face images out of source
  control and restrict access to them.
- Configure production CORS origins explicitly; localhost-only development
  origins in main.py are not a production allow-list.
- Run application instances behind a managed process supervisor and use
  migration deployment steps separate from API startup.
- Size SQLAlchemy connection pools according to database capacity and the
  number of application workers before changing engine configuration.
- Use structured logging and alerting around startup-trigger installation,
  listener failures, authentication failures, and background jobs.

15. MAINTENANCE CHECKLIST
==========================================================================

Adding an endpoint
  1. Define or extend the schema contract.
  2. Implement service behavior and authorization.
  3. Add controller orchestration.
  4. Add the route and register it in the appropriate router composition
     module.
  5. Add tests for authorization, invalid input, and success/error paths.

Changing data storage
  1. Update the SQLAlchemy model.
  2. Create and review an Alembic migration.
  3. Update schema, service, controller, and route contracts as required.
  4. Check relevant query indexes and backfill requirements.
  5. Test upgrade and rollback behavior on non-production data.

Adding cacheable reference data
  1. Cache serialized values, never request-bound ORM objects.
  2. Key caches by every authorization, context, and filter dimension.
  3. Define TTL and explicit invalidation when source data changes.
  4. Preserve fresh reads for permissions and user-specific access scope.

Pre-release checks
  - Apply Alembic migrations in a staging-equivalent environment.
  - Validate protected endpoints with permitted and non-permitted users.
  - Verify static-upload and face-enrollment paths have suitable storage
    permissions.
  - Confirm listener/scheduler ownership avoids duplicate execution across
    multiple API workers.
  - Run automated tests once a backend test suite is introduced. No dedicated
    backend tests directory exists in the current inventory.

16. OWNERSHIP SUMMARY
==========================================================================

When locating a change:
- Endpoint URL or HTTP behavior: routes/.
- Request orchestration: controllers/.
- Business rule or database query: services/.
- Table or relationship: models/ plus migrations/.
- Payload format: schemas/.
- Login, permissions, hierarchy, or record scope: core/ and dependency/.
- Real-time communication: routes/admin/websockets/ and websockets/.
- Reminders: models/reminders.py, services/reminders_service.py,
  database_triggers/, listeners/, scheduler/, and WebSocket modules.
- Face enrollment/recognition: employee_management, employee_face_profiles,
  services/face/, utils/face_embedding.py, and upload utilities.

Update this file in the same change set whenever a maintained backend module,
migration, deployment surface, or architectural boundary is added, removed,
or materially repurposed.
