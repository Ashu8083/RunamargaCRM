RUNAMARGA CRM — Alembic Database Migration Reference

1. What is Alembic?

Alembic is a database migration tool used with SQLAlchemy. It tracks changes to database structure over time.

Simple way to remember:

Git tracks code changes.

Alembic tracks database structure changes.

2. Our Database Stack

Python 3.10

SQLAlchemy 2.0

psycopg 3

PostgreSQL 18

Alembic

Application flow: Python → SQLAlchemy → psycopg → PostgreSQL 18

3. What We Have Done

Installed Alembic
Installed Alembic inside the project's .venv.

Initialized Alembic
Ran: alembic init migrations

Created Base
Created app/models/base.py using SQLAlchemy DeclarativeBase.

Connected Alembic to model metadata
Updated migrations/env.py to import Base and set target_metadata = Base.metadata.

Connected Alembic to the database
Alembic reads .env through app/config/settings.py and builds the PostgreSQL connection URL.

4. Current Database Setup

PostgreSQL: 18

Host: localhost

Port: 5432

Database: runamarga_crm_new

User: postgres

Existing/reference database: runamarga_crm

5. Configuration Flow

.env → settings.py → database.py → SQLAlchemy → PostgreSQL

.env → settings.py → migrations/env.py → Alembic → PostgreSQL

Both SQLAlchemy and Alembic use the same database configuration.

6. Important Alembic Files

alembic.ini
Main Alembic configuration.

migrations/env.py
Connects Alembic to application settings and SQLAlchemy metadata.

migrations/versions/
Stores migration files.

migrations/script.py.mako
Template used to create migration files.

7. Migration Workflow

1. Create or modify a SQLAlchemy Model.

2. The model inherits from Base.

3. The model becomes part of Base.metadata.

4. Run: alembic revision --autogenerate -m "description"

5. Alembic compares model metadata with the database structure.

6. Alembic creates a migration file in migrations/versions/.

7. Review the migration file.

8. Run: alembic upgrade head

9. Alembic applies the migration to PostgreSQL.

8. What Does `alembic current` Do?

It only checks which Alembic migration revision the database is currently at. It does not create a migration or change tables/data.

Simple meaning: “What migration version is my database currently on?”

9. Common Commands

alembic current
Show the current database migration revision.

alembic revision --autogenerate -m "message"
Generate a migration from model/database differences.

alembic upgrade head
Apply all pending migrations.

alembic history
Show migration history.

alembic downgrade -1
Move back one migration.

10. Simple Mental Model

SQLAlchemy Models → Base.metadata → Alembic Migration → PostgreSQL

Models define the intended database structure. Alembic records the changes needed to move the database from one structure/version to another.

11. RUNAMARGA Rule

The existing runamarga_crm database is reference-only. The new backend uses runamarga_crm_new. For tracked schema changes, modify the SQLAlchemy model, generate a migration, review it, and apply it with Alembic.

Runamarga CRM Authentication – How It Works

Purpose: This document explains the authentication architecture we are building for the new Runamarga CRM, the role of each file/component, the OTP flow, JWT access/refresh tokens, database storage, security, and the automatic refresh flow.

1. Overall Architecture

The authentication flow is intentionally separated into layers:

Frontend → Route → Controller → Service → Database

The route handles HTTP/FastAPI concerns, the controller coordinates the request, the service contains authentication/business logic, and the database stores employee and refresh-session data.

3. Employee Authentication

The Employee table is the source for determining whether a person is allowed to log in.

email identifies the employee.

deleted_at must be NULL.

deactivate must be false.

status must be active.

4. OTP Request Flow

Endpoint:

POST /auth/request-otp

Request schema already exists as RequestOTPRequest:

emailId

device (optional)

ipAddress (optional)

location (optional)

Flow:

Frontend sends emailId.

auth_routes.py receives the HTTP request.

auth_controller.py calls create_login_otp().

auth_service.py finds the Employee by email.

The employee's status/deactivation/deletion are validated.

A cryptographically secure 4-digit OTP is generated.

The OTP is hashed with SHA-256 before storage.

The hash and expiry time are stored on the employee.

OTP expiry is currently 5 minutes.

For development/testing, the OTP is currently returned in the response. In production it should be sent through the real OTP delivery mechanism.

5. OTP Verification Flow

Endpoint:

POST /auth/verify-otp

Request schema already exists as VerifyOTPRequest:

emailId

otp

deviceId (optional)

device (optional)

ipAddress (optional)

location (optional)

Find the employee by email.

Validate that the employee is active and not deactivated/deleted.

Ensure an OTP was requested.

Check that the OTP has not expired.

Hash the submitted OTP and compare it with the stored hash.

Clear the stored OTP fields so the OTP can be used only once.

Create a short-lived access JWT.

Create a longer-lived refresh JWT.

Hash the refresh JWT and store its hash in auth_tokens.

Return the authentication result during development. Later, tokens will be moved to secure HttpOnly cookies.

7. What Is Inside the JWT?

The current access JWT payload contains:

sub: employee ID, stored as a string.

type: access.

exp: expiration timestamp.

The refresh JWT uses the same basic structure but has type=refresh and a longer expiration. Sensitive personal or business information should not be placed in the JWT payload.

8. Why Access Tokens Are Not Stored in the Database

The access token is short-lived and self-verifying. The backend verifies its JWT signature and expiration using the JWT secret. This avoids a database lookup for the token on every API request.

If access tokens were stored and checked in the database on every request, every protected API call could require an additional database lookup. That is unnecessary for this design.

9. Why Refresh Tokens Are Stored

A refresh token represents a longer-lived login session/device. Its hash is stored in auth_tokens so the server can validate and revoke individual sessions.

Example:

Employee 1 – laptop session – valid

Employee 1 – phone session – valid

Employee 1 – old laptop session – revoked

10. auth_tokens Table

The new table contains fields for:

employee_id – which employee owns the session.

token_hash – SHA-256 hash of the refresh token.

token_type – currently refresh for stored sessions.

expires_at – refresh-session expiration.

revoked_at – allows a session to be revoked.

ip_address – optional login/session metadata.

device_id – optional device identifier.

device_type – optional device type.

latitude / longitude – optional login location metadata.

created_at – session creation time.

token_hash is unique. employee_id is not unique, so one employee can have multiple device sessions.

11. Security Model

OTP is not stored in plaintext; only its SHA-256 hash is stored.

OTP expires after 5 minutes.

OTP is cleared after successful verification.

Access JWTs are short-lived.

Refresh tokens are stored only as hashes in the database.

JWT signing uses a secret key and HS256 in the current implementation.

Production JWT_SECRET_KEY must be a strong secret supplied through secure configuration/environment management, not the development fallback.

Production traffic must use HTTPS.

Tokens should ultimately be placed in HttpOnly and Secure cookies, with an appropriate SameSite policy.

Do not put sensitive information inside JWT payloads.

12. Browser Cookie Design (Production)

The current development endpoint returns the tokens as JSON so that the flow can be tested. The planned production design is to set the tokens as secure cookies.

Access token → HttpOnly + Secure cookie.

Refresh token → HttpOnly + Secure cookie.

JavaScript should not directly read the tokens.

The browser automatically sends the cookies to the backend.

13. Automatic Access-Token Refresh

This is the part that addresses the old CRM problem where an access token sometimes needed a manual page refresh.

User logs in once.

Access JWT is valid for about 30 minutes.

When the access token expires, the frontend calls POST /auth/refresh.

The backend receives the refresh token.

The backend verifies that it is a valid refresh JWT.

The backend hashes the refresh token and checks the corresponding session in auth_tokens.

The backend rejects the session if it is expired or revoked.

The backend creates a new short-lived access JWT.

The new access token is returned/set as the access cookie.

The user continues working without manually refreshing the page.

14. Logout

The planned logout flow is to revoke the current refresh session by setting revoked_at and clear the browser cookies. Because the access token is short-lived, it naturally becomes invalid when it expires.

15. Multiple Devices

employee_id is intentionally not unique in auth_tokens. Each login/device can have its own refresh session.

Example: the same employee can log in on a laptop and phone, producing separate refresh-session rows.

16. Authentication and RBAC

Authentication answers: 'Who is this employee?' Authorization/RBAC answers: 'What is this employee allowed to do?'

JWT subject identifies the employee.

Employee role identifies the broad role.

Contexts distinguish operating scope such as global, agent, RM, or team-lead contexts.

Permissions determine allowed actions.

Data scope (for example agent_id or rm_id on applications) determines which records the employee can see/manage.

19. Simple Mental Model

OTP proves the user can complete the login challenge. The access JWT proves the request is from an authenticated employee for a short period. The refresh token represents the longer-lived login session. auth_tokens lets the server control those longer-lived sessions. RBAC and context permissions decide what the authenticated employee can actually access.
